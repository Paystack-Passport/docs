Webhooks tell you when something happens on your integration — a deposit arrives, a conversion
settles, a verification is approved — without polling for it.

Every delivery uses the same envelope. The interesting part is `event_object`: it carries the **same
body as the matching REST resource**, plus a few fields that only make sense on an event. So if you
already handle `GET /v1/conversions/{id}`, you already know how to read a `conversion.success`
payload.

## Subscribe by category

You don't subscribe to individual events. You subscribe to **categories** — families of related
events — when you [create a webhook endpoint](/api-reference/openapi#tag/notification-webhooks/POST/v1/notifications/webhooks),
and receive every event in the family.

| Category | Events you receive |
| --- | --- |
| `onramp` | `onramp.awaiting_deposit`, `onramp.funds_received`, `onramp.processing`, `onramp.success`, `onramp.failed`, `onramp.returned` |
| `offramp` | `offramp.created`, `offramp.funds_received`, `offramp.processing`, `offramp.success`, `offramp.failed`, `offramp.returned` |
| `conversion` | `conversion.created`, `conversion.funds_received`, `conversion.processing`, `conversion.success`, `conversion.failed`, `conversion.returned` |
| `transfer` | `transfer.processing`, `transfer.success`, `transfer.failed` |
| `deposit` | `deposit.received`, `deposit.held`, `deposit.confirmed`, `deposit.failed` |
| `kyc` | `kyc.approved`, `kyc.rejected` |

<Note>
  New endpoints are created **inactive**. Store the `signing_secret` from the create response — it is
  shown once — then activate the endpoint with `PATCH /v1/notifications/webhooks/{id}`
  `{ "active": true }`. Nothing is delivered until it is active.
</Note>

## The envelope

Every event, in every category, arrives in this shape:

```json
{
  "event_id": "evt_1b8dbe64-1f4e-5a2c-9c31-6d9a51a0f0c2",
  "event_type": "conversion.success",
  "event_category": "conversion",
  "event_developer_id": "int_01HXYZABC1234567890ABCDEFG",
  "api_version": "v1",
  "event_created_at": "2026-09-30T09:12:44.000Z",
  "event_object_id": "con_01KPBH8MD6R7YDJ82T4D6M3V1T",
  "event_object_status": "success",
  "event_object_changes": { "status": ["processing", "success"] },
  "event_object": { }
}
```

| Field | What it is |
| --- | --- |
| `event_id` | Unique id for this event, `evt_` prefixed. Stable across retries — use it to deduplicate. |
| `event_type` | The event, e.g. `conversion.success`. Branch on this. |
| `event_category` | The family the event belongs to. |
| `event_developer_id` | Your integration's public id. Useful if one receiver serves several integrations. |
| `api_version` | Envelope version. `v1` today; a breaking change to the shape bumps it. |
| `event_created_at` | When the event **happened** — not when it was delivered. A retry keeps the original time. |
| `event_object_id` | The id of the resource the event is about (`con_…`, `txn_…`, `tfr_…`). |
| `event_object_status` | The resource's status at the moment of the event. |
| `event_object_changes` | `{ "status": [previous, new] }` on a real status change; `null` when nothing changed (a replay, or an event that doesn't move the status). `previous` is `null` on a first transition. |
| `event_object` | The resource itself. Shapes below. |

Signature headers and how to verify them are covered in
[Verify webhook signatures](/webhooks/verify-signatures).

## When each event fires

### Onramps, offramps and conversions

These three run the same lifecycle, so they emit the same six events.

| Event | Fires when |
| --- | --- |
| `onramp.awaiting_deposit` | The onramp is created and waiting for the payer's deposit. Show them `deposit_instruction`. |
| `offramp.created` / `conversion.created` | The resource is created and accepted. |
| `*.funds_received` | Your funds arrived and were recognised. Work has not finished. |
| `*.processing` | The conversion or payout is in flight. |
| `*.success` | Done. The destination has been credited. **Terminal.** |
| `*.failed` | Could not complete. Read [`failure_reason`](/api-reference/failure-reasons). **Terminal.** |
| `*.returned` | Funds were sent back to their origin. **Terminal.** |

<Tip>
  `funds_received` and `processing` are separate events on purpose — `funds_received` is your cue
  that the money is in, which is usually what you tell a customer about. Don't treat either as
  final; wait for `success`, `failed` or `returned`.
</Tip>

### Transfers

| Event | Fires when |
| --- | --- |
| `transfer.processing` | The payout has been submitted. |
| `transfer.success` | The payout completed. **Terminal.** |
| `transfer.failed` | The payout failed, was cancelled, or was reversed. **Terminal.** |

A cancelled or reversed transfer arrives as `transfer.failed` — `failure_reason` tells you which
(`cancelled`, `reversed`, or another code).

### Deposits

| Event | Fires when |
| --- | --- |
| `deposit.received` | Funds detected but not yet final — a crypto deposit seen on-chain before confirmation, or a cross-currency deposit that has just been priced. |
| `deposit.held` | Credited but withheld pending review. `metadata.hold_reason` is `tier_limit`, `payin_frozen` or `payin_disabled`. |
| `deposit.confirmed` | Settled and spendable from the wallet balance. **Terminal.** |
| `deposit.failed` | The deposit could not be credited. **Terminal.** |

Two paths are worth planning for:

- **A held deposit sends two events.** `deposit.held` first, then `deposit.confirmed` when the hold
  is released. Don't treat `held` as final, and don't expect it on every deposit.
- **A [cross-currency deposit](/api-reference/auto-conversion) never reaches a terminal
  `deposit.*` event.** It stays at `received`, and the `conversion.*` events carry the outcome.
  Waiting for `deposit.confirmed` on that path waits forever.

### Verifications

| Event | Fires when |
| --- | --- |
| `kyc.approved` | The verification passed. `customer.tier` is the customer's **new** tier. |
| `kyc.rejected` | The verification was declined. Read [`failure_reason`](/api-reference/failure-reasons#verification-kyc-codes). |

Only final outcomes are sent. Intermediate progress — a customer opening the link, submitting
documents, or being asked to resubmit — is visible on
`GET /v1/customers/{customerId}/verifications` and does not emit a webhook.

## Payloads

`event_object` is the REST resource body **plus** event-only fields. Two groups of extras:

| Extra field | On | Why it's there |
| --- | --- | --- |
| `actual_source_amount`, `actual_destination_amount`, `actual_rate` | onramp, offramp, conversion | What actually settled, versus the quoted `rate` and amounts. Reconcile against these. |
| `terminal_at` | onramp, offramp, conversion, transfer | When the resource reached its terminal state. `null` before then. |
| `deposit_timestamp` | deposit | When the deposit was observed (on-chain time or the payer's transfer time), which differs from the row's `created_at`. |
| `wallet`, `customer`, `credential` | cross-currency deposits only | Which wallet the money lands in, whose it is, and which credential was funded — no second API call. |

<Warning>
  Reconcile money against `actual_*`, not against `rate`/`destination_amount`. The quoted values are
  what you were promised; the `actual_*` values are what settled. They are `null` until the
  economics are known.
</Warning>

## Delivery

<Steps>
  <Step title="Return 2xx quickly">
    Acknowledge with any `2xx` as soon as you have stored the event. Do the work afterwards — a slow
    handler looks like a failure and gets retried.
  </Step>
  <Step title="Expect at-least-once, not exactly-once">
    A delivery can arrive more than once. `event_id` is stable across every retry of the same event,
    so record the ids you have processed and ignore repeats.
  </Step>
  <Step title="Don't rely on order">
    Events are not guaranteed to arrive in lifecycle order. Use `event_object_status` and
    `event_object_changes` rather than assuming the previous event already landed, and ignore an
    event that would move a resource backwards from a terminal state.
  </Step>
</Steps>

A given resource emits a given event **at most once** — so two upstream changes that map to the same
event (a cancelled transfer and then a reversed one, both `transfer.failed`) reach you once, not
twice.

### Debugging a delivery

| You want to | Use |
| --- | --- |
| See why deliveries are failing | [`GET /v1/notifications/webhooks/{id}/logs`](/api-reference/openapi#tag/notification-webhooks/GET/v1/notifications/webhooks/{id}/logs) — attempt history with the HTTP status you returned, error, and latency |
| See what is queued | [`GET /v1/notifications/webhooks/{id}/events`](/api-reference/openapi#tag/notification-webhooks/GET/v1/notifications/webhooks/{id}/events) — pending events, oldest first, with the payload that will be sent |
| Replay one you missed | [`POST /v1/notifications/webhooks/{id}/send`](/api-reference/openapi#tag/notification-webhooks/POST/v1/notifications/webhooks/{id}/send) with the event's `event_id` as `event_idempotency_key` |

<Note>
  Replay only delivers to an **active** endpoint — an inactive one returns `409 invalid_status`.
  Activate it first, then resend.
</Note>
